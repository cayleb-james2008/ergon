Before accepting the artifact I exercised the guided first run the way the owner will, and found two REAL defects in the shipped code:
1. **Interactive credential entry was dead on a real TTY.** `first-run --credentials` printed "an interactive credential run needs a
   terminal secret reader" and exited: `collectCredentials()` never instantiated the documented default TTY reader, and every unit test
   injected one, so the defect was invisible to the suite. This matters because it is exactly the "collects credentials once, into
   their fields only" step. Found by driving the CLI under a real PTY.
2. **Wrong absorb classification** in the real inventory: `@opencode-compat/dsh-bridge` (a third-party bridge that runs unmodified
   OpenCode aisdk provider plugins as DSH adapters) was classified ABSORB with the claim that the fleet's `llm-pi-ai` provides those
   routes. The fleet mounts `llm-pi-ai` with an EMPTY providers config (schema default `{}`), so it offers no such routes — the
   plan would have told the owner to remove a plugin whose capability the fleet does not carry. Found by reading the real inventory
   output myself.
Both are fixed by the builder (commit 2183bf0, cherry-picked into the release branch): the default TTY reader is wired (raw mode set
before the prompt; regression test that fails on the old code; real-PTY end-to-end: fake key accepted, stored via the in-host control
op, value absent from transcript and logs, store 0600), and ABSORB now requires the fleet to ACTUALLY provide the capability (bridge
is KEEP-AS-DEPENDENCY; capability map comment records the lesson; upgrader's REMOVE reason now says owner-confirmed, never
automatic). I independently re-ran the PTY flow on the final artifact: `status: written`, `stored: OPENCODE_GO_API_KEY via
control-op`, fake value not echoed, lands in the scratch store once (0600), nothing outside the store.
