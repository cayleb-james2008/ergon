### Terms (each defined here once, before first use)

- **Lane**: one agent session in the fleet (roles such as `lead`, `builder`, `checker`, `researcher`).
- **uid 1000**: the owner's own login account number on this machine. The fleet host and every lane run under it, so the machine cannot tell a lane's action from the owner's by user id.
- **Owner Elevation**: a way for an agent to file a request to run ONE exact command as root, which only the owner can approve by typing his password at the machine. **Broker**: the part inside the fleet host that holds requests. **Entry program**: the small root-owned program that shows the command and takes the password. **D1** (design decision 1): the one-time install of the entry program's files by the owner under sudo.
- **Tier A / Tier B**: the two classes of confirm tickets the fleet policy raises. Tier A confirms spend (for example budget raises). Tier B confirms policy and grants (registering a participant, issuing a token, a seat route). **Ticket**: one pending confirm request held by the fleet daemon.
- **L4-A** (A1 to A4): the design's item that moves every Tier A and Tier B confirm onto the password-gated entry program and then turns file confirms off (**the A3 flip**).
- **Case W / case C**: W (worst, assumed) means lane shells are not walled off from the owner's files, sockets and network, so they act as him; C means they are sandboxed and cannot see them. **G40**: the read-only probe from a real lane shell that shows which case holds. It is item 40 of the design's checklist and also named P0b below.
- **Lane 6**: Team E's security-review gate (`upkeep-lead`). A hard gate: it must pass before the privileged helper ships (B4).
- **P0 to P7 (Leg 4)**: the owner-run proof steps in design section 13 (sudo behaviour, G40, install, file, enter, check, negative probes, timeout probe). They are not the Leg 3 Duet probes that also run from P0 to P6; this pack always says "Leg 4 P-steps" or "Duet probes".
- **T-numbers**: rows of the design's threat table (section 11): **T3** a fake or substituted password prompt (not closable at uid 1000); **T5** keystroke capture; **T13** request flooding, where the caps are advisory; **T20** abuse of the control socket's owner operations; **T29** a network-facing uid-1000 service (the Duet courier, a relay session) as attacker. **G17, G39**: checklist gates for the compositor key-bind question and the shape of sudo's journal line.
- **Courier / C0 / N1 / bus / facade**: the courier is the Leg 3 process that carries Duet's mail; **C0** is the probe that its sandbox holds (else it is not enabled); **N1** is the planned, unbuilt adapter that lets Nox read bus mail; the **bus** is the fleet's message layer; the **facade** is the fleet's MCP tool surface, closed at 15 tools.

The owner opens a secure prompt on his own machine, sees the exact command, types his password once, and sudo runs that command once. ### 2.2 The Tier B confirm path as it works TODAY on this machine

This is the interim, and it is not the design's confirm path. The baseline is B4: Tier B is refused (fail-closed) and no agent patches the confirm directory. Two later rulings made exceptions: the one hand-placed confirm for 100008 (11:55 ET, `165500Z`) and the owner's own sitting confirms for 100018 and its token ticket (15:22 ET, `202249Z`).

- The stock route is `dsh-fleet confirm <ticket>`, which runs `pkexec --user fleet` on the root-owned `/usr/local/bin/dsh-fleet-confirm`. That helper hardcodes `/var/lib/fleet/state/confirms` and requires the `fleet` user [record: `finish-A-3-owner-elevation-gap.md` section 1; design section 12 finding 2].
- The live consolidated host runs as the owner (uid 1000) and reads `<DSH home>/fleet/state/confirms`, and accepts only files owned by its own uid whose JSON has `pkexec_uid` equal to the peer uid [design section 12 finding 1; gap report]. The retired `fleet-dsh` unit is inactive; `/run/fleet/` is still `fleet`-owned [observed]. So the stock helper writes to a directory the live host never reads, and `dsh-fleet` is not even on PATH [record: comment in `owner-sitting/confirm-100018.sh`].
- What actually happens: the owner runs a script in his own terminal (`board/owner-sitting/confirm-100018.sh`, `confirm-100019.sh`). It re-reads the ticket from the daemon (`ticket-get`) and the stored grant row, refuses if either is not exactly the expected one, prints "WHAT YOU ARE APPROVING", needs him to type YES, runs `sudo -k; sudo -v` (his password again), then writes the confirm JSON into the live host's confirms directory and logs a `logger -t dsh-fleet-confirm` line. Per claude-finish `20261102T202800Z` (15:28 ET) the owner did this for ticket 100018 (register `ext:delegator`) and 100019 (issue its token) at 15:18 and 15:20 [record; I did not read the live database].
- **What that interim does and does not give.** The password is checked only by the script. The host never sees or verifies it; the host trusts the file. A lane running as uid 1000 can write the same file directly, so the script is an honest process, not a control. The executing session's safety layer refused to hand-place the 100018 confirm for exactly this reason [record: claude-finish `T200800Z` section 3]. Hand-placing has been used only under your explicit rulings: ten Tier A confirms (o1 budget raises, tickets 100002 to 100017) and one Tier B (100008, checker seat route) [record: `TIER-A-GRANTS-LEDGER.md`]. The plugin hard-codes the approver label `cayleb-local:polkit` on all of them, so its own chain does not show the true route (design A1 fixes this).
- **Consequence for the future flip (design A3).** After `policy.file-confirms` goes off, Tier A spend confirms also need the owner's password at the machine. Ten Tier A confirms were hand-placed in one day (14:25Z to 20:02Z), which shows how often that would be.

### 2.3 The threat model in plain words

Every lane runs as uid 1000, the owner's own user account. So any lane can write the fleet database, drop a file in the confirms directory, call every owner operation on the control socket, and call the facade with a token it can read. The design assumes this worst case (case W) until G40 shows lanes are sandboxed (case C) [design sections 3, 11].

- **Forged confirm file by a lane running as the owner: a known, current gap.** Today any lane holding a Tier B ticket can confirm it [design section 12 finding 1; read from code, not run]. What the design does, as item L4-A: **A1** record the true route and channel in the grant row; **A2** route every Tier A and Tier B ticket confirm through the same password prompt, as a request to run `/usr/bin/true tb:<12 hex of the ticket hash>` (`ta:` for Tier A), and treat the ticket as confirmed only when sudo's own system-log line saying it succeeded for exactly that command is found (the log field naming the program as `/usr/bin/sudo`, which a process running as the owner cannot fake); **A3** then flip `policy.file-confirms` off so confirm files confirm nothing, but only after A2 is proved on the real machine; **A4** never widen directory permissions, retire the pkexec path. Until the flip, a file confirm stays forgeable and is recorded `confirm-file`, `authenticated 0`.
- **A fake or substituted password prompt (T3): not closable at uid 1000.** A lane can edit the app card, CLI or broker so the owner's genuine button opens the lane's own look-alike. The root-owned entry program only makes the genuine one tamper-evident. The design says this is the main residual risk and the owner must be told before the first run [design T3, section 1 item 2].
- **Password theft from memory or the wire.** Closed by design: the prompt process cannot be memory-inspected by another process of the same user and leaves no crash dump; the password travels over a private connection that a same-user process cannot re-open (tested: a plain pipe can be re-opened, this cannot); the program runs with a fixed clean environment; and the password is accepted once, only for the matching request. Keystroke capture through the compositor's runtime bindings (T5, G17) is unverified.
- **Display equals execution.** One process holds one argv, shows it and runs it. A forged database row changes what is shown and what runs together, never one without the other (design 5.2).
- **The caps are advisory.** Rate limits, cooldowns, suspension and `lock` can be cleared by a lane with a shell (T13, T20). The real controls are only that no prompt opens by itself and the owner reads the command.
- **Network-facing uid-1000 services** (the Duet courier, a relay session) join the attacker set (T29) and must be sandboxed (Lane 6 HIGH condition, courier sandbox C0).

### 3.2 The `elevate.list` / deny question, stated plainly (ruled: L4-2)

**The question.** Should Nox's side, or the owner's phone through Nox, be able to list the pending elevation requests and deny them (or approve-mark them) through the fleet's MCP facade, as two new tools `elevate.list` and `elevate.decide`? **Where the design raises it.** Design s1 (D4), s7 last paragraph, s8.3, s9 item 6, s14 item 13; RECONCILE section 2 row R4 and issue 10. The design's names are `elevate.list` and `elevate.decide`; you wrote "elevate.list/deny": deny is the half that matters, because an approve is only a marker (L4-3).

**What each would do.**
- `list` would show: id, state, requester, age, expiry, the 12-hex binding hash, classification, and `remote_decision` (s8.1, s14 item 9). No argv, no output, no password. The full command is only on the machine (`elevate show`).
- `deny` ends the request at once; nothing runs; the same hash is refused for one hour; three denials in 24 hours suspend that agent (advisory). It fails safe.
- `approve` (E1 reading) runs nothing, opens no prompt; it extends the expiry and puts "approved remotely, unverified" on the machine prompt.

**Who may call what, today.**
- Agent tools `elevate_request`, `elevate_status`, `elevate_withdraw`: roles `lead` and `builder` only; caller taken from the session, not arguments; a caller sees only its own requests (s7). These are not facade tools.
- Owner operations (`list`, `show`, `deny`, `lock`, `unlock`, `elevate-decide`, `elevate-fetch`, `elevate-outcome`): the control socket admits any uid-1000 peer not in `fleet-hands.service`. In case W that is every lane. They are recorded `authenticated 0` and are advisory: a lane can deny others' requests, lock, unlock, or "decide" (s8.2, T20). The socket is `srw-rw-rw-` owned by the owner at `/run/user/1000/fleet/control.sock` [observed].
- Facade: nobody, because neither tool exists. The facade is nine core tools plus six bus tools and is closed (cited as your 10:48 ET ruling in RECONCILE; on file through R4 at 11:55 ET). The `duet` token is `scope-denied` on all but four bus calls (s11 T29; gate 43).

**Why the design says no tools now.** (1) A facade token is a file any uid-1000 process can read (RECONCILE issue 12), so a tool would let any lane that reads a token deny other agents' requests, or plant an "approved remotely" note on the owner's prompt, a nudge toward typing the password. (3) The password is typed at the machine anyway, so a remote decision adds only a veto and a marker. What exists today as a "remote decision" is whatever a uid-1000 process types into `elevate-decide`: a relayed Nox ruling is indistinguishable from a lane saying it.
