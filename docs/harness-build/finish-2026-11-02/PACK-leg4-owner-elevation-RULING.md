## 1. What you are ruling on, and what it unblocks

Owner Elevation lets an agent file a request to run ONE exact command as root. The owner opens a secure prompt on his own machine, sees the exact command, types his password once, and sudo runs that command once. Nothing but the typed password counts as authority; rows, buttons, taps and relayed messages are routing and record only (design section 1, section 9). The same password-gated prompt also replaces the broken, forgeable Tier A/B confirm path (item L4-A, design section 12). That second part is the one the rest of the fleet waits on: the design says every live Leg 2 grant and every Leg 3 token comes after it.

You are ruling on fifteen items (section 3: L4-1 to L4-11, L4-4b, L4-12, L4-13, L4-14). Four need your word before anything else moves: **L4-1** (the root-install approach), **L4-4** (run the G40 probe and who runs it), **L4-5** (adopt Lane 6's condition that the confirm prompt shows the ticket's real detail), and **L4-6** (does a live Leg 3 `duet` token wait for L4-A; this collides with your sequence 3, 4, 1). The `elevate.list/deny` question you asked for is stated plainly in 3.1. Four further items are decisions the design or RECONCILE leaves with you: the G40 follow-on (L4-4b), the advisory control operations (L4-12), the Tier A scope of the new confirm path (L4-13), and the deferred writable app panel (L4-14, not blocking). The build can start in a worktree on fake sudo without any of them; the owner-run root install and the real run cannot.

Not asked today: the real elevation run. It is an owner's-home-sitting act and is "not on today's list" (`OWNER-PRIVILEGED-PACK-2026-11-02.md` item 4).

### 2.2 The Tier B confirm path as it works TODAY on this machine

This is the interim, and it is not the design's confirm path.

- The stock route is `dsh-fleet confirm <ticket>`, which runs `pkexec --user fleet` on the root-owned `/usr/local/bin/dsh-fleet-confirm`. That helper hardcodes `/var/lib/fleet/state/confirms` and requires the `fleet` user [record: `finish-A-3-owner-elevation-gap.md` section 1; design section 12 finding 2].
- The live consolidated host runs as the owner (uid 1000) and reads `<DSH home>/fleet/state/confirms`, and accepts only files owned by its own uid whose JSON has `pkexec_uid` equal to the peer uid [design section 12 finding 1; gap report]. The retired `fleet-dsh` unit is inactive; `/run/fleet/` is still `fleet`-owned [observed]. So the stock helper writes to a directory the live host never reads, and `dsh-fleet` is not even on PATH [record: comment in `owner-sitting/confirm-100018.sh`].
- What actually happens: the owner runs a script in his own terminal (`board/owner-sitting/confirm-100018.sh`, `confirm-100019.sh`). It re-reads the ticket from the daemon (`ticket-get`) and the stored grant row, refuses if either is not exactly the expected one, prints "WHAT YOU ARE APPROVING", needs him to type YES, runs `sudo -k; sudo -v` (his password again), then writes the confirm JSON into the live host's confirms directory and logs a `logger -t dsh-fleet-confirm` line. Per claude-finish `20261102T202800Z` (15:28 ET) the owner did this for ticket 100018 (register `ext:delegator`) and 100019 (issue its token) at 15:18 and 15:20 [record; I did not read the live database].
- **What that interim does and does not give.** The password is checked only by the script. The host never sees or verifies it; the host trusts the file. A lane running as uid 1000 can write the same file directly, so the script is an honest process, not a control. The executing session's safety layer refused to hand-place the 100018 confirm for exactly this reason [record: claude-finish `T200800Z` section 3]. Hand-placing has been used only under your explicit rulings: ten Tier A confirms (o1 budget raises, tickets 100002 to 100017) and one Tier B (100008, checker seat route) [record: `TIER-A-GRANTS-LEDGER.md`]. ### 2.3 The threat model in plain words

Every lane runs as the owner's own user account (user id 1000). So any lane can write the fleet database, drop a file in the confirms directory, call every owner operation on the control socket, and call the facade with a token it can read. The design assumes this worst case ("case W": lanes are not walled off from the owner's files and sockets, so they act as him) until G40 shows lanes are sandboxed ("case C": lanes cannot see his home, his runtime sockets or the network) [design sections 3, 11]. "Lanes run as him" means that the machine cannot tell a lane's action from his own by user id.

- **Forged confirm file by a lane running as the owner: a known, current gap.** Today any lane holding a Tier B ticket can confirm it [design section 12 finding 1; read from code, not run]. What the design does, as item L4-A: **A1** record the true route and channel in the grant row; **A2** route every Tier A and Tier B ticket confirm through the same password prompt, as a request to run `/usr/bin/true tb:<12 hex of the ticket hash>` (`ta:` for Tier A), and treat the ticket as confirmed only when sudo's own system-log line saying it succeeded for exactly that command is found (the log field naming the program as `/usr/bin/sudo`, which a process running as the owner cannot fake); **A3** then flip `policy.file-confirms` off so confirm files confirm nothing, but only after A2 is proved on the real machine; **A4** never widen directory permissions, retire the pkexec path. Until the flip, a file confirm stays forgeable and is recorded `confirm-file`, `authenticated 0`.
- **A fake or substituted password prompt: not closable at uid 1000.** A lane can edit the app card, CLI or broker so the owner's genuine button opens the lane's own look-alike. The root-owned entry program only makes the genuine one tamper-evident. The design says this is the main residual risk (the "substituted prompt") and the owner must be told before the first run [design T3, section 1 item 2].
- **Password theft from memory or the wire.** Closed by design: the prompt process cannot be memory-inspected by another process of the same user and leaves no crash dump; the password travels over a private connection that a same-user process cannot re-open (tested: a plain pipe can be re-opened, this cannot); the program runs with a fixed clean environment; and the password is accepted once, only for the matching request. Keystroke capture through the compositor's runtime bindings is unverified (T5, G17).
- **Display equals execution.** One process holds one argv, shows it and runs it. A forged database row changes what is shown and what runs together, never one without the other (design 5.2).
- **The caps are advisory.** Rate limits, cooldowns, suspension and `lock` can be cleared by a lane with a shell (T13, T20). The real controls are only that no prompt opens by itself and the owner reads the command.
- **Network-facing uid-1000 services** (the Duet courier, a relay session) join the attacker set (T29) and must be sandboxed (Lane 6 HIGH condition, courier C0).

### 3.1 The `elevate.list` / deny question, stated plainly

**The question.** Should Nox's side, or the owner's phone through Nox, be able to list the pending elevation requests and deny them (or approve-mark them) through the fleet's MCP facade, as two new tools `elevate.list` and `elevate.decide`? Or only at the machine, through `dsh-fleet elevate list` and `deny`, plus one owner operation, `elevate-decide`, on the control socket?

**Where the design raises it.** Design s1 (D4), s7 last paragraph, s8.3, s9 item 6, s14 item 13; RECONCILE section 2 row R4 and issue 10. The design's names are `elevate.list` and `elevate.decide`; `decide` takes approve or deny. You wrote "elevate.list/deny": deny is the half that matters, because an approve is only a marker (L4-3).

**What each would do.**
- `list` would show: id, state, requester, age, expiry, the 12-hex binding hash, classification, and `remote_decision` (s8.1, s14 item 9). No argv, no output, no password. The full command is only on the machine (`elevate show`).
- `deny` ends the request at once; nothing runs; the same hash is refused for one hour; three denials in 24 hours suspend that agent (advisory). It fails safe.
- `approve` (E1 reading) runs nothing, opens no prompt; it extends the expiry and puts "approved remotely, unverified" on the machine prompt.

**Who may call what, today.**
- Agent tools `elevate_request`, `elevate_status`, `elevate_withdraw`: roles `lead` and `builder` only; caller taken from the session, not arguments; a caller sees only its own requests (s7). These are not facade tools.
- Owner operations (`list`, `show`, `deny`, `lock`, `unlock`, `elevate-decide`, `elevate-fetch`, `elevate-outcome`): the control socket admits any uid-1000 peer not in `fleet-hands.service`. In case W that is every lane. They are recorded `authenticated 0` and are advisory: a lane can deny others' requests, lock, unlock, or "decide" (s8.2, T20). I observed the socket is `srw-rw-rw-` owned by the owner at `/run/user/1000/fleet/control.sock`.
- Facade: nobody, because neither tool exists. The facade is nine core tools plus six bus tools and is closed (your 10:48 ET ruling; RECONCILE facade contract). The `duet` token is `scope-denied` on all but four bus calls (s11 T29; gate 43).

**Why the design says no tools now.** (1) A facade token is a file any uid-1000 process can read (RECONCILE issue 12), so a tool would let any lane that reads a token deny other agents' requests, or plant an "approved remotely" note on the owner's prompt, a nudge toward typing the password. (2) Nothing reads the facade on Nox's behalf yet: `nox` has no pull route, adapter N1 is unbuilt (claude-finish `T213500Z` section 5; RECONCILE R2). (3) The password is typed at the machine anyway, so a remote decision adds only a veto and a marker. What exists today as a "remote decision" is whatever a uid-1000 process types into `elevate-decide`: a relayed Nox ruling is indistinguishable from a lane saying it.

**Options.** (a) No tools. (b) Read-only `elevate.list` only. (c) Both. **Recommendation: (a)**, from the design and RECONCILE R4; you confirmed it at 11:55 ET (`T165500Z`: "R4: CONFIRMED - no facade tool for elevation decisions"). The reconcile file and design s1 were not updated, so I restate it here to close it. If it is ever reopened **[exec-rec]**: add `elevate.list` before `decide`, and if `decide` is added, make it deny-only (no approve marker), only after N1 exists and G40 shows tokens are confined, with a named gap and your ruling per the facade rule.
